## What to compare

Use the same scenario in every direction:

- Ternary Health is hiring a Senior Frontend Systems Engineer.
- Kavya Menon has a strong evidence fit and one disclosed domain gap.
- The current fixed proposal is ₹5.8L for 14 weeks at 28 hours per week.
- Application version 2 answers material gig terms version 3.
- A 48-hour exact-version selection request is waiting for response.

Suggested comparison path:

1. Enter as a freelancer and inspect discovery, gig evidence, proposal creation, application Q&A, and selection.
2. Switch to the client role and inspect applicant comparison, Kavya’s dossier, private shortlist/advancement, and exact selection.
3. Edit the proposal to create a new immutable version and observe selection invalidation.
4. Send a fresh request as the client.
5. Accept as the freelancer and open the engagement.
6. Exercise lifecycle progression and secure contact share, mask, reveal, and revocation states.

State persists in browser local storage and is shared across all concepts for fair comparison. Use each concept’s **Reset** control or the root index reset to restore the reference scenario. The root gallery also provides deterministic **baseline**, **revision**, **invalidated**, **expired**, and **engaged** presets so the same consequential state can be compared directly.

## Comparing the final collection

Directions 21–26 are the final six operating models:

- **Bench:** a focused work session with contextual actions and an exact durable record.
- **Measure:** a fourteen-week instrument coupling scope, capacity, timing, and quote consequences.
- **Crosscheck:** a requirements-by-version crosshair showing both parties and historically effective authority.
- **Orbit:** a semantic orbital field retaining parent context while priority and depth change.
- **Weave:** an inspectable source-to-consequence weave for evidence, versions, authority, and permission.
- **Current:** a continuous flow where revision diverts a record and exact acceptance carries it into work.

The final collection uses two light, two dark, and two mixed visual systems. Motion is action-triggered, interruptible, and replaced by immediate state changes under `prefers-reduced-motion`. The interfaces use semantic DOM and SVG underlays rather than inaccessible canvas rendering.

## Comparing the expansion

- **Tempo** starts with deadlines, available capacity, and a credible 14-week delivery plan.
- **Duet** keeps the client brief and specialist position visible on opposite sides of an alignment spine.
- **Aperture** moves through market, brief, application, exact terms, and engagement by semantic depth.
- **Facet** normalizes evidence, gaps, terms, availability, versions, and stages into a decision lattice.
- **Fold** keeps Find, Propose, Review, Confirm, and Work visible as one expandable journey.

The original five concept implementations remain unchanged. Directions 06–10 share only the mock domain and workflow transitions with them; each expansion direction has its own components, layout model, tokens, responsive rules, and interaction grammar.

## Comparing directions 11–15

- **Tally** separates reviewed suitability from structured commercial scope and line-item allocation.
- **Lane** keeps several records visible across marketplace stages; unlike Fold, it is concurrent rather than a single expandable journey.
- **Command** replaces persistent navigation with direct intent while retaining visible, clickable alternatives for every command.
- **Proofroom** treats reviewed work as a collection of evidence artifacts rather than a profile or abstract score.
- **Trace** shows causal source lineage; unlike Relay’s chronology, it explains where a claim originated and what it authorizes.

Facet normalizes comparable axes; Tally composes one exact commercial scope. Relay records what happened; Trace explains which source enabled the consequence. Concepts 01–10 remain frozen, while Directions 11–15 use independent components, visual systems, navigation models, and responsive behavior.

## Comparing the hybrid collection

Directions 16–20 deliberately combine two compatible interaction grammars. The parent concepts contribute ideas, not imported components, CSS, tokens, or page shells.

- **Harbor — Northline × Tempo:** Northline contributes the compact action register and persistent context; Tempo contributes deadlines, capacity, and the credible 14-week delivery plan.
- **Accord — Covenant × Duet:** Covenant contributes the durable case record and redline treatment; Duet keeps the client and specialist positions visible around a central alignment spine.
- **Vector — Command × Trace:** Command contributes direct, keyboard-enhanced intent; Trace makes the source, authority, and consequence of each action inspectable.
- **Atelier — Aperture × Proofroom:** Aperture contributes semantic depth and retained parent context; Proofroom contributes evidence artifacts, coverage, and explicit absence.
- **Index — Monument × Facet:** Monument contributes full-width typographic rhythm and expanding rows; Facet contributes normalized evidence, gap, availability, version, and commercial axes.

Suggested hybrid comparison:

1. Compare **Harbor** and **Accord** as credible production directions: operating workspace versus bilateral record.
2. Compare **Vector**, **Atelier**, and **Index** as bolder interaction models: command provenance, evidence depth, and typographic normalization.
3. Revise Kavya’s proposal in each hybrid and inspect how the old selection becomes invalid.
4. Switch to the client, send a fresh 24/48/72-hour request, then return as Kavya to accept it.
5. Compare how the accepted engagement preserves terms and handles masked contact consent, reveal, and revocation.

The root gallery labels every hybrid’s two parents. Concepts 01–15 remain byte-for-byte unchanged inside their own component and stylesheet directories.

## Verification and dependency note

The suite is verified with `npm run build`, `npm run lint`, and `npm test`.
The production dependency audit currently reports
`GHSA-qwww-vcr4-c8h2` through `react-router`. The advisory applies to React
Router's server-side RSC action handling; this suite is a static,
client-rendered `BrowserRouter` application with no RSC server, actions,
backend, or deployment runtime, so the affected execution path is absent.
The audit's suggested forced fix would downgrade `react-router-dom` across a
breaking boundary and has intentionally not been applied.
