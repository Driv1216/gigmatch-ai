## Expiry and authoritative time

`private.project_selection_request_expiry_locked` is the sole 7G expiry projector. The
caller locks the gig, captures one `authoritative_now`, locks the request through the
helper, and uses the same time for all checks and writes. Only the successful
`pending → expired` update appends `selection_request_expired`.

The existing gig lifecycle RPC now uses this helper. An effective request still blocks
pause; a due stored-pending request is projected once and pause may proceed. Selection
responses that reach the expiry boundary return an expired result after committing the
projection, allowing FastAPI to return the stable 409 without rolling the expiry event
back.

## Token design

Three domain-separated SHA-256 state tokens are generated by service-only database read
RPCs and recomputed under mutation locks:

- send token: exact gig/application identities, stage/current application version,
  material gig version, lifecycle/operations, effective request, open revision, gig-change
  response state, and warning requirement;
- management token: request identity/status/expiry/bindings, current application/gig state,
  and client ownership;
- response token: request status/expiry, bound/current versions, stage/gig state, open
  revision state, winner, and engagement.

The browser never supplies trusted identities, versions, snapshots, expiry, commercial
terms, warning metadata, acknowledgement actor/time, or event data.

## Transactional idempotency

`private.selection_operations` is an immutable, RLS-enabled, non-browser operation ledger.
It records actor + request UUID, canonical fingerprint, operation kind, aggregate
references, and engagement reference.

Replay/conflict resolution occurs inside the same PostgreSQL transaction as send,
cancellation, decline, revision response, or acceptance. Authorization/resource
resolution precedes replay; exact replay precedes ordinary current-state validation.
Therefore terminal retries return the authoritative existing request/engagement, while a
key reused for another operation returns `idempotency_conflict`. A different-key second
acceptance returns `selection_response_already_resolved` and creates nothing.

## Readiness and resend behavior

Send readiness is revalidated under locks for ownership, `advanced` stage, complete current
proposal, exact current material response, valid commercial/timeline/availability/scope
terms, acknowledgement, active/unpaused/unfilled gig, no effective request, no open 7F
revision, no winner/engagement, and current token.

Intake closure and a passed application deadline do not block selection. Unanswered Q&A
does not block selection. Minor normalized corrections retain the material pointer and do
not invalidate the request; material changes do.

Resends enforce:

- same-term expired request: allowed;
- client-cancelled request: allowed except terminal gig cancellation, with the structured
  cancellation reason preserved;
- decline/remain-interested with unchanged terms: blocked;
- revision requested without a genuinely new application version: blocked;
- decline/withdraw while application remains withdrawn: blocked by stage readiness;
- minor correction alone: not new selection terms.

Fresh requests link the latest relevant prior request.

## Response workflows and atomic acceptance

- Cancel: request becomes cancelled; application remains Advanced.
- Decline/remain: request becomes declined with `remain_interested`; proposal and Q&A are
  preserved.
- Decline/withdraw: request becomes declined with `withdraw_completely`; application becomes
  Withdrawn using the existing 7D reason contract. Existing 7E/7F terminal behavior clears
  shortlist state and makes child workflows non-actionable.
- Revised terms: request becomes `revision_requested` with structured categories; application
  remains Advanced; no 7F revision request is manufactured.
- Accept: exact frozen versions and acknowledgement atomically accept the request, confirm
  the selected application, fill the gig, create exactly one version-2 engagement, close
  only other active applications with `another_applicant_selected`, preserve terminal
  histories, run existing shortlist/Q&A/revision effects, append events, and commit.

No partial result survives a forced failure.

## Lock order

The implemented order is:

```text
gig
→ selection request
→ selected application
→ remaining active applications by UUID
→ trigger-owned review/Q&A/revision child state
→ engagement
→ events
```

The 7E and 7F application triggers update only the current application's child aggregate.
No new scanning trigger was introduced.
